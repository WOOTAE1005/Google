마음담음 — 프로젝트 리스크 및 한계점 정리
2026-08-21

전부 실제로 존재하는 문제이되 심각도는 다름 — 맨 아래 3단계 분류를 우선 참고할 것.

====================================================
1. 기술 스택 리스크
====================================================

1) React 19 + Tailwind v4
   둘 다 나온 지 얼마 안 된 최신 버전. 지금까지는 문제없이 동작했지만,
   특정 라이브러리가 아직 완전히 지원하지 않는 호환성 이슈가
   남은 기간에 나타날 가능성이 LTS급 버전보다 높음.

2) Gemini API 의존성
   무료 등급 할당량이 예측 불가능(실제로 다른 프로젝트에서 "한도 0" 문제 겪음).
   폴백 로직이 있어 서비스가 죽지는 않지만, 데모 당일 실제 AI 응답 대신
   매번 같은 폴백 문구만 나올 위험.

3) Express + Vite 미들웨어 통합
   프론트+백엔드를 한 프로세스로 합친 구조 — 배포는 단순해지지만
   Next.js 같은 표준 프레임워크보다 비정석적이라 문제 발생 시
   참고할 사례가 적음.

4) Firebase 경로 미검증
   로그인/Firestore 동기화/Storage 업로드 전부 실제 프로젝트에 연결해
   끝까지 테스트한 적 없음. 코드는 맞게 짜여 있으나 실동작 여부는 미지수.

5) 자동화 테스트 전무
   단위/통합 테스트가 하나도 없어 수동 확인에만 의존.
   여러 곳을 동시에 고치면 어딘가 조용히 깨질 위험.

6) Storage 규칙이 완전 개방형
   storage.rules가 로그인 없이 누구나 이미지 업로드 가능(용량·타입만 제한).
   데모용으로는 무방하나 실제 배포 시 스팸성 업로드에 취약.

====================================================
2. 보안·비용
====================================================

7) /api/generate-message 요청 제한 없음
   같은 사람이 연속 호출하거나 다른 사이트에서 직접 호출해도
   막는 장치가 없음. 배포 시 Gemini 할당량/비용 소진 위험.

8) 사용자 입력 길이 제한 없음
   추가 요청사항(자유 텍스트)에 길이 캡이 없어, 아주 긴 입력이
   그대로 프롬프트에 들어가 토큰 비용 증가 또는 프롬프트 인젝션 여지.

9) API 서버 출처(origin) 검증 없음
   배포된 엔드포인트를 다른 웹사이트에서도 그대로 호출 가능한 상태.

====================================================
3. 개인정보·콘텐츠
====================================================

10) 익명 통계의 이름 필터링에 구멍 있음
    analytics.ts의 sanitizeWord가 "차장님"처럼 존칭 붙은 이름은 걸러내지만,
    존칭 없는 맨 이름("김상우")은 못 걸러냄. 코드 주석에도 스스로 명시된 한계.

11) 부적절 콘텐츠 필터 없음
    자유 입력이 그대로 AI에 전달되고 카카오톡으로 공유까지 되는데,
    욕설/부적절 내용을 걸러내는 장치가 없음.

====================================================
4. 오늘 추가한 기능(형식 선택 확장, 카카오 실공유)의 허점
====================================================

12) 카카오 이미지 공유 조용한 폴백
    Kakao 키는 있는데 Firebase Storage가 없으면 조용히 텍스트만 공유됨.
    사용자에게 "왜 이미지가 없는지" 안내가 없어 혼란 가능.

13) OG 메타태그 없음
    index.html에 og:title/og:image 등이 없어, 공유된 링크(webUrl) 자체가
    나중에 재공유될 때 미리보기가 비거나 어색하게 나올 수 있음.

14) html-to-image 폰트 렌더링 리스크
    카드를 PNG로 만들 때 커스텀 폰트(Noto Serif KR, Pretendard)가
    캔버스에 실패 없이 잘 박히는지 실제로 검증한 적 없음.
    라이브러리 특성상 흔한 실패 지점.

====================================================
5. 디자인 일관성 · 검증 커버리지
====================================================

15) 카드 팔레트 13개 중 12개가 사이트 톤과 불일치
    사이트 전체 크롬은 "장미빛 잉크"로 리스킨했지만, 카드 자체의 기존
    12개 팔레트(단청 슬레이트, 로얄 인디고 등)는 그대로라 브랜드 톤이 따로 놈.

16) 리스킨 커버리지 미검증
    카드 레이아웃 5종 x 팔레트 13종 = 65개 조합을 전부 눈으로
    확인하지 않음. 일부 조합에 예전 앰버 톤 잔재나 대비 문제가
    남아있을 가능성 배제 못 함.

17) 모바일 미검증
    카카오톡 공유가 핵심 기능인데, 실제 모바일 뷰포트에서 UI가
    안 깨지는지 직접 확인한 적 없음.

18) 접근성(a11y) 미고려
    스크린리더/키보드 탐색 등을 전혀 고려하지 않음.

====================================================
6. AI 출력 신뢰 · 외부 의존성
====================================================

19) 형식별 글자수 규칙이 강제되지 않음
    봉투문구 10~25자 등은 프롬프트상의 "지시"일 뿐, Gemini가 안 지켜도
    코드가 걸러내거나 재시도하지 않음.

20) 폰트가 외부 CDN(jsdelivr, Google Fonts) 의존
    Gemini/Firebase/Kakao 외에도 폰트 CDN이 느리거나 막히면
    데모 중 기본 서체로 깨져 보일 수 있음.

====================================================
7. 확장성 · 엔지니어링 성숙도
====================================================

21) Firestore 분석 문서 병목 가능성
    익명 통계가 문서 하나를 계속 increment하는 구조라, 트래픽이 커지면
    그 문서에 쓰기가 몰릴 수 있음 (현재 규모에선 무관).

22) 번들 사이즈 미측정, 코드 스플리팅 없음
    React+Firebase+motion+html-to-image+Kakao SDK가 전부 한 번에 로드됨.
    실제 로딩 속도를 측정해본 적 없음.

23) CI/CD 없음
    커밋마다 타입체크/빌드를 자동 검증하는 장치(GitHub Actions 등)가 없어
    수동 확인에 의존.

24) 1인 개발 — 코드 리뷰 부재
    데모 당일 예상 못 한 버그가 나오면 혼자 대응해야 함.

====================================================
8. 심각도 3단계 분류 (우선순위 판단용)
====================================================

[1단계] 데모 당일 실제로 터질 수 있는 것 — 진짜 신경 써야 함
 - 2) Gemini API 할당량 리스크
 - 14) html-to-image 폰트 렌더링 리스크
 - 12) 카카오 이미지 공유 조용한 텍스트 폴백
 - 17) 모바일 미검증

[2단계] 실제 문제지만, 통제된 데모 환경에선 안 드러날 가능성이 높은 것
 - 7) API 요청 제한 없음 / 8) 입력 길이 제한 없음 / 9) 출처 검증 없음
 - 10) 익명화 허점 / 11) 콘텐츠 필터 부재
 - 19) AI 출력 길이 미검증
 - 15) 카드 팔레트 브랜드 불일치 / 13) OG 메타태그 없음
 - 20) 외부 CDN 폰트 의존 / 16) 리스킨 커버리지 미검증

[3단계] 실제 문제라기보다 "엔지니어링 성숙도" 심사 질문 대비용
 - 4) Firebase 미검증
 - 18) 접근성 없음
 - 24) 1인 개발 프로세스
 - 23) CI/CD 없음
 - 22) 번들 사이즈 미측정
 - 21) Firestore 분석 병목

결론: 데모 준비 시간은 1단계에 집중하고, 2단계는 "알고 있다"는 정도로
충분하며, 3단계는 Q&A 답변 준비용으로 남겨둔다.
